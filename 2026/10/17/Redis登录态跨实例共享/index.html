Redis 登录态如何支持多实例部署

如果登录信息只保存在某一台应用服务器的内存里，那么同一个用户的下一次请求落到另一台服务器时，后者可能找不到登录状态。这是多实例部署中常见的会话共享问题。

1. Session 与共享存储

传统 Session 通常由服务器保存状态，浏览器通过 Cookie 携带会话标识。单实例时简单直接；多实例时可以配置会话粘滞，也可以把会话状态放入共享存储。共享存储能让任一应用实例读取状态，但需要考虑过期、失效和存储故障。

在黑马点评类项目中，常见的教学实现是自己生成随机 Token，并将用户登录信息保存到 Redis。这是一个应用层 Token 方案，不等同于自动获得了 Spring Session 的功能，也不应与 JWT 混为一谈。

2. 登录和请求校验流程

Redis 键可以按 login:token:{token} 组织，值保存必要的用户标识和权限上下文。不要把密码、完整支付凭据等敏感数据作为登录缓存内容。

3. 双拦截器职责

一种常见拆分是：第一个拦截器尽量匹配所有请求，为已登录用户刷新 Token 过期时间并设置当前用户；第二个拦截器只保护必须登录的路由，检查上下文并在未登录时拒绝请求。

这样，浏览公开页面时也可以保持登录态活跃；受保护接口仍要做认证和授权。具体的拦截顺序应由注册顺序和 order 明确控制，公开路由也要有清楚的白名单。

4. ThreadLocal 的清理

应用可用 ThreadLocal 暂存当前请求的用户信息，方便后续服务获取。但 Web 容器会复用线程，因此请求完成后必须清理，通常在拦截器的 afterCompletion 或请求过滤器的 finally 中执行 remove()。否则下一个请求可能读到前一个请求留下的数据。

ThreadLocal 只解决同一 JVM 的线程上下文传递，不会跨服务器共享数据，也不适用于未正确传递上下文的异步任务。

5. 过期、登出与安全边界

  • Token 应具备足够随机性，不能使用用户 ID 或递增数字。
  • 登出时删除 Redis 中对应 Token，并清理客户端保存的值。
  • 过期时间应与产品的登录策略一致；续期操作要避免无限延长不符合预期的会话。
  • 传输应使用 HTTPS；不要把 Token 写入 URL、日志或公开截图。
  • 关键操作仍需做权限校验，不能只因为“有 Token”就信任请求参数里的用户 ID。

6. 与 JWT 的区别

Redis Token 是服务端可查询、可主动删除的状态；JWT 通常把声明放在签名令牌中，服务端可在验证签名和有效期后读取声明。JWT 的签名不等于加密，载荷不应放入机密信息；立即撤销 JWT 通常还需要额外状态或短有效期策略。

7. 小结

本方案把登录状态放入共享 Redis，使多个应用实例能读取同一份状态。它依赖 Redis 可用性和过期策略，仍需防护 Token 泄露、权限混淆和 ThreadLocal 未清理等问题。
